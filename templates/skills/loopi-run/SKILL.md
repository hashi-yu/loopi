# 自動実装パイプラインを実行する

引数: $ARGUMENTS

設定は `loopi.config.json`（基準ブランチ・参照ドキュメント・保護パス・テストコマンド・モデル・上限）を参照する。

## 1. 事前確認
- `gh issue view <番号>` で issue を読み、次を確認する。欠けていれば実行せず、ユーザーに補足を提案する
  - 背景・意図、受け入れ条件、触ってよいファイル、スコープ外が埋まっている
  - 受け入れ条件がテストで確認できる形になっている
  - issue に書かれた関連ドキュメント（spec / ADR など）のパスが実在する
- `git status` で、未コミット・未 push のドキュメント変更が残っていないか確認する（パイプラインは `origin/<baseBranch>` から作業するため、push されていない変更は実装担当に見えない）

## 2. 実行
- Bash ツールで **バックグラウンド実行**（run_in_background）する:
  `npx github:hashi-yu/loopi run $ARGUMENTS`
- 再実行の場合、成功済みの工程（実装・一次レビュー・最終レビュー）は自動でスキップされる。レビューをやり直させたいときだけ `--fresh` を付ける
- 数分〜数十分かかる。ユーザーには「開始しました。終わったら報告します」とだけ伝え、ポーリングはしない
- 途中経過を聞かれたら `tail -n 40 logs/issue-<番号>.log` で確認する

## 3. 完了後
`logs/issue-<番号>.status.json` を読み、`status` に応じて報告する。ログ全体は読まず、必要なら `tail` で末尾だけ見る。作業フォルダの場所は status.json の `worktree` にある。

- **merged**: PR の URL、最終レビューの summary、採用/却下した指摘の件数と主な内容を 5 行程度で報告。`git pull` を実行してローカルを最新にする
- **pr_waiting**: 自動マージしなかった理由（`reasons`）を伝え、`gh pr diff` で差分を読んで自分でもレビューする。問題なければユーザーにマージしてよいか確認し、OK なら `gh pr merge <番号> --squash` → `git push origin --delete <ブランチ>` → `git worktree remove <作業フォルダ>` → `git pull`
  - `reasons` に「passed でない受け入れ条件がある」が含まれる場合: 続く要素に条件の文が列挙されている。PR コメントの対応表（検証方法・判定結果・根拠）を見て、条件ごとに何が足りないかをユーザーに報告する。テストを足す、または条件に `（レビュー確認）` を付けるなら、再実行の前に issue を直す
- **escalated**: 停止理由（`reason`, `detail`）を説明し、次の選択肢を提示する
  - issue や参照ドキュメントを修正して再実行（既存の作業フォルダを再利用する）
  - 作業フォルダを対面で直してから再実行
  - 中止（`git worktree remove --force <作業フォルダ>` と `git branch -D <ブランチ>`）
- **interrupted**: 外部から停止された（Ctrl-C や kill）。壊れてはいないので原因の切り分けは不要。再実行すると成功済みの工程を飛ばして続きから進むことを伝え、同じコマンドで再実行する
- **error**: エラー内容を伝え、原因（認証切れ、モデル ID、利用上限、設定ファイルの不備など）を切り分ける

## 注意
- 決定済みの設計判断（ADR）の変更は、ユーザーと対面で合意してから行う
- パイプラインの判断（却下した指摘など）に疑問があれば、PR コメントの記録を根拠にユーザーへ伝える
