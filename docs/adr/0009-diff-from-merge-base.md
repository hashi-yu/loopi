# 0009 差分は基準ブランチとの分岐点から測る

状態: 採用（0003 の「基準ブランチとの差分」を置き換え。#29）

## 背景

0003 は再実行時のスキップを「基準ブランチとの差分」で判定し、実装は `origin/<baseBranch>` と作業フォルダを直接比べていた。実行中や再実行前に `git fetch` で `origin/<baseBranch>` が進むと、基準ブランチ側だけで入った変更が逆向きの変更として差分に混ざる。そのため、他の PR が触った保護パスで escalate し、`holdOnChange` で確認待ちになり、レビュー合格キーが無効になってレビューをやり直していた。レビュー担当にも無関係な差分が渡る。

## 決定

- 差分は、作業ブランチと `origin/<baseBranch>` の分岐点（`git merge-base HEAD origin/<baseBranch>`）から作業フォルダ（未コミットの変更を含む）までの変更とする。初回実装のスキップ、保護パス、`holdOnChange`、レビュー中の差分の変化、レビュー合格キー、最終レビューキーはすべてこの差分で判定する
- 分岐点は判定のたびに求め、保存しない。マージ直前に基準ブランチを取り込んだ後は、分岐点が取り込んだ `origin/<baseBranch>` そのものになる
- `git diff --merge-base` は使わない。git 2.30 未満でも動くように、分岐点のコミット ID を求めてから比べる

## 結果

- 基準ブランチが進んでも、再実行時に実装・レビューの記録がそのまま使える。1 件ずつマージしてから次を回す、という運用上の制約が要らなくなる
- 作業フォルダを再利用するとき、基準ブランチの取り込みはこれまでどおりマージ直前まで行わない。0003 で「#5 で見直し中」としていた点は、差分のずれがこの決定で解消し、最新の基準ブランチでのテストはマージ直前に行っているため、見直さないことにした（#5 は見送り）
- 検討して採らなかった案: 再実行時に基準ブランチを先に取り込む（#5）。loopi は PR 作成まで commit しないため、途中の commit か stash が要り、工程の変更になる
