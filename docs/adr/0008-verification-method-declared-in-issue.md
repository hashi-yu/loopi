# 0008 受け入れ条件の検証方法は issue を書く人間が宣言する

状態: 採用（0005 の「テストで確認できない受け入れ条件がある」を置き換え）

## 背景

`src/run.ts` の配線、シグナルハンドラの登録、`docs/spec/` への追記のような条件は、AGENTS.md の「テストで外部プロセスを起動しない」により検証するテストが存在し得ない。最終レビューはこれを `missing` にし、レビュー担当が差分と文書を読んで満たしていると確認していても確認待ちになる（#6 / PR #12 では 7 条件中 3 条件）。loopi 自身の issue は run.ts の配線が本体なので、毎回起きる。

## 決定

- 受け入れ条件ごとに**検証方法**を issue を書く人間が宣言する。条件の末尾に `（レビュー確認）` があればレビュー担当が差分と文書を読んで判定し、無ければテストの結果で判定する
- 最終レビューは条件ごとに検証方法・判定結果・根拠を返す。判定結果の意味は検証方法ごとに定める
  - テスト: 該当テストが通った → `passed` / 落ちた → `failed` / 該当テストが無い、または条件を実質的に検証していない → `missing`
  - レビュー確認: 差分と文書が条件を満たす → `passed` / 満たさない、または反する → `failed` / 判断できる材料が無い → `missing`
- 自動マージの判定は変えない。すべて `passed` のときだけ通し、`passed` でない条件は確認待ちの理由に条件の文ごとに列挙する
- レビュー担当は印に従う。印のある条件がテストで検証できたはずだと考えても、判定は変えずに非ブロッキングの懸念として書く
- すべての条件がレビュー確認の issue も自動マージしてよい。止めたいときは `noAutomergeLabel` か `holdOnChange` を使う

## 結果

- 判断の主体が分かれる。何をテストで縛るかは issue を書く人間が決め、レビュー担当は宣言された方法で確かめるだけになる。レビュー担当が自分の判断で「読んだから通す」余地は無い
- 0005 の確認待ち条件「テストで確認できない受け入れ条件がある」は「`passed` でない受け入れ条件がある」に変わる。0007 の「そこだけを変える issue では確認待ちになる」は、印を付ければ自動マージまで進む
- 検討して採らなかった案: 判定結果に `verified` を足す（結果と方法が 1 つの軸に混ざる）。レビュー確認だけの issue は常に確認待ちにする（「既存テストが通る」のような形式的な条件で回避できる）。テストで偽の外部コマンドを起動できるようにする（AGENTS.md の方針変更で、別の判断として扱う）
