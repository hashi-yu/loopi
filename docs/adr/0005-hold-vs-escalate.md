# 0005 人間に回す判断を「確認待ち（hold）」と「停止（escalate）」に分ける

状態: 採用（確認待ち条件のうち受け入れ条件の判定は 0008 で置き換え）

## 背景

自動マージまで回す以上、「人間が見るべきもの」を機械的に決める必要がある。すべてを人間に回せば自動化の意味がなく、すべて自動で通せば設計判断や仕様の変更まで無断でマージされる。

## 決定

人間に回す状況を 2 種類に分け、終了コードと `status` で区別する。

**確認待ち（`pr_waiting`、終了コード 0）**: 実装はレビューを通っており、PR はある。マージするかどうかだけ人間が決める。

- 最終レビューが `hold`
- `passed` でない受け入れ条件がある（検証方法はテストまたはレビュー確認 → 0008）
- `holdOnChange` のパスを変更している
- issue に `noAutomergeLabel` が付いている
- `--no-merge`

**停止（`escalated`、終了コード 2）**: パイプラインの前提が崩れており、PR を作らない（または作った後でもマージしない）。issue にコメントして理由を残す。

- 実装担当が `protectedPaths` を変更した
- テストが上限回数で通らない、レビューが上限ラウンドで収束しない
- 取捨選択で「決定済みの設計判断に反する／仕様にない判断が必要」と判断された
- レビュー中に差分が変わった、変更が無い
- 基準ブランチとの競合、取り込み後のテスト失敗、最終レビュー前の詳細テストの失敗

**エラー（`error`、終了コード 1）** は環境の問題（認証、モデル ID、設定ファイルの不備、外部コマンドの失敗）で、人間の判断ではなく修復が必要なもの。

## 結果

- 自動マージの最後の門は Claude の最終レビューで、受け入れ条件の対応表（検証方法・判定結果・根拠）を根拠に出す（→ 0008）
- `pr_waiting` の理由はすべて列挙する（1 つ解消しても別の理由で止まることを事前に分かるように）
- 外部から止められた場合（SIGTERM / SIGINT）は `interrupted`（終了コード 3）。人間の判断も修復も要らず、再実行すれば続きから進む（#6）
