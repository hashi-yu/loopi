# 0001 実装とレビューでモデルの系統を分ける

状態: 採用

## 背景

同じモデルに実装とレビューをさせると、自分の出力を自分で採点することになり、見落としが再現される。一方で、レビューの指摘をそのまま実装に流すと、好みやスタイルの指摘まで修正され、issue の意図から外れていく。

## 決定

工程ごとに役割と系統を固定する。

| 工程 | 担当 | 権限 |
|---|---|---|
| 実装・修正 | pi（`models.pi`。既定は安価なモデル） | 作業フォルダを変更できる |
| 一次レビュー | Codex | 読み取りのみ。重大な問題だけを挙げる |
| 取捨選択・最終レビュー | Claude（`models.claude`。強いモデル） | 読み取りのみ（`Read,Grep,Glob`） |

- 一次レビューの指摘は、そのまま実装担当に渡さない。Claude が issue・仕様・ADR に照らして採用/却下を決め、採用したものだけを「能力の低めなモデルが迷わず直せる具体的な指示」に書き換えて渡す
- 却下した指摘は理由付きで PR 本文に残す。最終レビューはその判断の妥当性も見る
- 実装担当には `git commit` をさせない。コミットはパイプラインが行う

## 結果

- 実装は安いモデルで回せる。判断が重い工程だけ強いモデルに寄せる
- レビュー担当がファイルを変更しない前提が成り立つので、レビュー中に差分が変わったら異常として停止できる
- 3 系統の認証（pi、Codex、Claude Code）が前提になる
